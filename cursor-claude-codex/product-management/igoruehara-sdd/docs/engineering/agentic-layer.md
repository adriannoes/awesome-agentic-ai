# The project's agentic layer

The same inputs from kickoff (stack, tools, process, domain) tune the layer that makes
**humans and agents operate the SDD pipeline**. Four artifact types, all versioned —
generated/proposed by `/kickoff` and evolved throughout the project.

## 1. Rules — how the agent should behave
- **`CLAUDE.md`** — conventions, ubiquitous language, layering rule, Definition of Done.
  Read in every session. (generated at kickoff)
- **`.claude/settings.json`** — permissions (allowlist of common stack commands, to reduce
  prompts) and **hooks**. ⚠️ Sensitive: confirm each permission/hook before saving.

## 2. Docs — the knowledge (the constitution)
vision · mvp-canvas · design · domain · spec · ADRs · glossary · context-map · roadmap · integrations.
The spec remains the **source of truth**.

## 3. Agents (subagents) — on-demand specialists
`.claude/agents/<name>.md` (see `docs/engineering/_templates/subagent.template.md`). Typical examples:
- **`spec-reviewer`** — validates testable acceptance criteria (*Definition of Ready* gate).
- **`domain-modeler`** — extracts ubiquitous language and aggregates from a spec; checks the glossary.
- **`adr-writer`** — drafts an ADR from a decision.
- **`<stack>-tester`** — runs and interprets the stack's tests (e.g., pytest, vitest).

## 4. Skills — reusable workflows
`.claude/skills/<name>/SKILL.md` (see `docs/engineering/_templates/skill.template.md`). Examples:
The 8 boilerplate skills, one responsibility each:

| Skill | Responsibility |
|---|---|
| **`/kickoff`** | orchestrates the constitution (discovery + 5 axes + generation) |
| **`/mapear`** | brownfield as-is → `assessment.md` (independent re-run) |
| **`/diagramar`** | high-level architecture in Mermaid → `diagrams.md` |
| **`/roadmap`** | builds/reviews the roadmap with the team |
| **`/camada-agentica`** | proposes/generates rules, subagents, skills, workflows/CI |
| **`/integracoes`** | team tools + MCPs (orthogonal to kickoff) |
| **`/nova-feature`** | loop per feature (tier → spec → tasks) |
| **`/validar`** | local UAT: gates, AC→test, SPEC_DEVIATION, DoD |
| **`/revisar-pr`** | SDD conformance gate on the PR/MR (posted via MCP) |
| **`/setup-ci`** | CI/CD pipeline that materializes the SDD gates |
| **`/metricas`** | Lead Time · Throughput · CD maturity → `metrics.md` |
| **`/auditar`** | validates pipeline conformance (frontmatter, links, traceability) |
| **`/evals`** | spec→code fidelity (AC per task/test, SPEC_DEVIATION) |
| **`/handoff`** | pauses/resumes via `docs/STATE.md` (continuity) |

- *Tools-aware* (generated by `/camada-agentica` if the MCP exists): **`/spec-to-jira`**, **`/publicar-confluence`**.

## 5. Workflows — pipeline automation
- **Hooks** (`settings.json`): `SessionStart` → `.claude/hooks/load-context.mjs` injects the base
  context (`alwaysApply: true`); run lint/test on `Stop`; warn when editing out of scope.
- **CI/CD** (`/setup-ci`): fail a PR that changes code **without an approved spec**; run the
  acceptance tests derived from `spec.md`. This is where the SDD gate becomes a pipeline.
- **PR/MR gate** (`/revisar-pr`): process conformance in review, complementing the
  harness `/code-review` (which hunts bugs).
- **Pipeline conformance** (`.github/workflows/esteira.yml` → `scripts/audit-esteira.mjs`):
  validates frontmatter, links, and specs on every PR. `/auditar` is the companion with judgment
  (traceability, orphan specs, DoD).

## How the inputs tune each artifact
| Kickoff input                     | Tunes                                                   |
|-----------------------------------|---------------------------------------------------------|
| Stack (e.g., Python/pytest)       | rules in `CLAUDE.md` · `<stack>-tester` · permissions   |
| Tools (Jira/Confluence)           | skills `/spec-to-jira`, `/publicar-confluence`          |
| Process (Scrum/Kanban)            | sprint prep workflow; roadmap cadence                   |
| Domain (bounded contexts)         | `domain-modeler` · glossary seeds                       |
| Observability                     | hooks/CI that check metrics and SLO                     |

> Principle: **propose with justification, generate only what is approved.** Anything not approved
> becomes an adoption roadmap item — no big-bang.
